# Long-chat browser profile

The latest-page window keeps fresh-open cost nearly flat between 1,000 and
50,000 stored events. Dense Markdown costs substantially more than total history
length. Returning to an old browser tab needs a separate path: replaying every
missed event still does work even when only 200 timeline rows are retained.

## Method

Measured on 2026-10-24 against the browser code at `025c111`, before the idle-resume
change. The server is the debug `browser_fixture` example, started through
`bin/dev-instance` with a separate database and a fake agent. No live chat was
copied or modified, and no provider was called.

The seed has deterministic prose, Markdown lists, code blocks, tables and grouped
tool calls/results. Three normal chats contain 1,000, 10,000 and 50,000 agent
events. A fourth repeats rich content thirty times per message, including
300-row tables. Events, timeline rows and DOM nodes are different counts.
This fixture does not cover uploaded images or image decoding.

Chromium ran headless at 1440 x 900 and 390 x 844, with fourfold CPU throttling.
Each case ran three times in the same browser context. HTTP cache behavior was
normal. Opening time is navigation start until the browser automation observes
rows with history loading complete; it includes polling overhead and is not an
exact paint timestamp. History HTTP time comes from Resource Timing and includes
transfer, not just server query execution. Five older-page requests exercise the
bounded history window. Then 120 animation frames scroll inside that window,
away from paging thresholds.

## Results

Values below are medians in milliseconds. DOM counts are after the fifth older
page on the last run. The retained row count was 166 or 167 because tool rows are
grouped. Raw measurements are in [the JSON artifact](long-chat-2026-10-24.json).

| Viewport | Events | Open | History HTTP | Older page | DOM elements after paging |
| --- | ---: | ---: | ---: | ---: | ---: |
| Desktop | 1,000 | 165 | 7.8 | 78 | 4,347 |
| Desktop | 10,000 | 165 | 10.6 | 82 | 4,347 |
| Desktop | 50,000 | 167 | 18.6 | 83 | 4,416 |
| Desktop | 1,000 dense | 494 | 25.6 | 501 | 56,982 |
| Phone width | 1,000 | 160 | 7.9 | 56 | 4,347 |
| Phone width | 10,000 | 159 | 9.9 | 69 | 4,347 |
| Phone width | 50,000 | 154 | 18.8 | 82 | 4,416 |
| Phone width | 1,000 dense | 506 | 24.4 | 486 | 56,982 |

The 95th-percentile animation-frame gap during interior scrolling was about
17.2 ms in every case. This synthetic scroll does not measure native touch
scrolling, interaction while a page is arriving, or Safari. Dense opening did
produce main-thread long tasks, including a 292 ms task in one desktop run.
A smooth interior scroll does not make a half-second paging pause acceptable.

Heap readings without forced garbage collection are retained in the JSON for
context, but should not be compared as retained-memory measurements.

## Resume behavior

A browser regression check simulates a phone becoming hidden while a second
device sends a message to the fake agent. After sixteen simulated minutes, the
phone returns. Before the fix, this check fails because no latest-history
snapshot is requested. The old stream has continued or resumed at its old cursor.

The fixed behavior uses the existing chat-selection path. After fifteen
minutes without a scroll-position change, it clears rendered rows, event context
and the chat cursor, reads the latest snapshot, then reconnects the stream at
that snapshot's cursor. Hidden documents wait until visibility or focus returns.
Brief absences keep the existing reading window. Draft text, pending sends and
attachments remain in the model.

The fixed browser check passes: one latest-history request precedes the resumed
chat stream, whose cursor comes from the new snapshot. The unfinished draft and
latest fake reply both survive. See [the resume result](long-chat-resume-2026-10-24.json).

A separate dense-chat typing check runs the fake agent's 80 reply events over eight
seconds at fourfold CPU throttling. All 59 typed characters, focus and caret
position survive. Input-to-next-animation-frame latency has an 18.3 ms 95th
percentile. This is a synthetic latency proxy, not an INP measurement. See
[the input result](long-chat-input-2026-10-24.json).

## Memory after resetting an idle window

The dense fixture has 166 displayed rows after paging. A forced garbage collection
before each reading separates retained JavaScript from uncollected garbage.

| State | Displayed rows | Live DOM elements | JavaScript heap bytes |
| --- | ---: | ---: | ---: |
| Before reset | 166 | 56,982 | 6,722,916 |
| Cleared, before history response | 0 | 114 | 5,940,032 |
| Latest snapshot populated | 42 | 15,252 | 6,424,956 |

Clearing releases the old DOM before the request returns. Reopening retains about
one quarter as many live elements in this stress case. The net JavaScript heap
reduction is only about 0.3 MB. This does not measure browser-native DOM memory,
renderer RSS, or decoded image memory. The bounded Markdown HTML cache remains
populated, so a chat reset does not release every cached string. See
[the memory result](long-chat-memory-2026-10-24.json).

## Repeat the checks

Build the browser assets and fixture executable. The executable is needed to run
the fake server; a compilation check alone cannot serve browser requests.

```sh
(cd web && npm run build)
cargo build -j4 --workspace --example browser_fixture
BOBLM_DEV_BIN="$PWD/target/debug/examples/browser_fixture" BOBLM_DEV_NO_BUILD=1 \
  bin/dev-instance start --name long-chat-profile --port 3027
```

Use a unique named `playwright-cli` session and the installed headless Chromium
path through a session configuration. Open the dev URL, authenticate with that
dev instance's token, then run the scripts by absolute path:

```sh
playwright-cli -s=YOUR_SESSION run-code --filename="$PWD/web/bench/long-chat.js"
playwright-cli -s=YOUR_SESSION run-code --filename="$PWD/web/bench/resume-chat.js"
playwright-cli -s=YOUR_SESSION run-code --filename="$PWD/web/bench/chat-memory.js"
playwright-cli -s=YOUR_SESSION run-code --filename="$PWD/web/bench/streaming-input.js"
```

The memory check explicitly collects garbage before each reading and delays the
history response so it can inspect the cleared window. The resume check adds fake
messages to its isolated chat. Run the baseline profile before the resume check
if you need identical seed counts. For a fresh seed, use a new dev-instance name.
Close only your Playwright session and stop the named dev instance afterward.

These measurements do not justify a native client. The next rendering target,
if paging pauses matter in practice, is dense rich content within the retained
window. Measure that on the owner's phone before choosing virtualization or
changing message presentation.
